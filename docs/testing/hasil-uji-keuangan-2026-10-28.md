Temuan yang muncul selama uji ini dan **sudah lulus retest**: dimensi XLSX semula `A1` sehingga pembaca streaming kehilangan data; email invoice revisi Transfer setelah kurang bayar semula tidak dikirim; invoice Tempo dengan due campuran semula hanya menampilkan due asli. Ketiganya diperbaiki oleh agent utama dan retest di atas menggunakan build QA baru. Jejak kegagalan awal tetap ada dalam log sebelum perbaikan.

Keterbatasan umum: pengujian ini membuktikan perilaku pada infrastruktur QA lokal dan data sintetis. Status PASS tidak menyatakan bahwa transaksi keuangan riil telah dicoba di produksi.

## Status kumulatif skenario

Laporan [tindak lanjut 27 Oktober](hasil-uji-tindak-lanjut-2026-10-27.md) menjadi baseline untuk ID lain. Enam ID P0 di atas berpindah ke PASS, sedangkan TMP-01 berpindah dari NOT RUN ke PARTIAL. Dengan demikian, dari **124 P0**: **40 PASS, 0 FAIL, 75 PARTIAL, 6 NOT RUN, 3 BLOCKED**. Dari **162 skenario**: **41 PASS, 0 FAIL, 102 PARTIAL, 16 NOT RUN, 3 BLOCKED**. Angka ini tidak berarti seluruh skenario telah diuji ulang atau lulus.

Tiga skenario OCR provider nyata (VER-08/09/10) masih BLOCKED karena kunci penyedia AI untuk QA belum tersedia. Pengujian dengan provider tiruan membuktikan alur dan penjaga keamanan, tetapi tidak membuktikan hasil OCR provider nyata.

## Rilis dan pemeriksaan produksi

Perbaikan dimensi XLSX, penjaga opsi AI, status cadangan, dan runtime backup dirilis terlebih dahulu. Perbaikan email invoice revisi serta rincian jatuh tempo PDF kemudian dirilis pada **28 Oktober 2026 pukul 10:58 WIB**, commit produksi `ced6664b` (sumber dengan tree identik: `a04fd53c`). Deploy berhasil membuat backup database sebelum mengganti container. API berstatus sehat; kedua portal dan endpoint `/api/v1/meta` merespons HTTP 200. Log API dan worker sesudah deploy tidak menunjukkan error awal.

Pemeriksaan baca saja dengan akun Superadmin produksi mengembalikan HTTP 200 untuk status OCR dan backup. `ai_active=false` serta `provider_ready=false`: opsi AI tersedia di Pengaturan tetapi tidak dapat diaktifkan sebelum penyedia dikonfigurasi; verifikasi manual tetap berjalan. `konfigurasi_api_siap=false` serta `perlu_tindakan=true`: cadangan terenkripsi database **dan objek** belum aktif karena tujuan penyimpanan/kunci penerima belum dikonfigurasi. Timer backup database lokal lama tetap berjalan; itu bukan bukti pemulihan cadangan offsite terenkripsi.

Tidak ada transaksi keuangan sintetis yang dibuat di produksi. Audit baca saja tidak menemukan invoice revisi Transfer yang sudah terbit tetapi kekurangan email cabang, sehingga tidak ada email historis yang perlu dikirim ulang. Uji pilot Tempo produksi masih membutuhkan cabang uji yang ditetapkan. Bukti pengujian terperinci berada di `/opt/temp/grahita-qa-finance-2026-10-28/` pada lingkungan kerja ini.

## Uji backup dan restore tambahan

Pada 28 Oktober, `TestPGBackupRestoreLingkaranPenuh` **PASS** memakai PostgreSQL 18.6 dan `pg_dump` 18.6 pada jaringan Docker QA terisolasi. Tes menjalankan migrasi 0001–0019, membuat tiga cabang serta satu bukti dan satu dokumen sintetis, lalu menghasilkan dump age-encrypted. Sinkronisasi objek memasukkan kedua berkas ke manifest; restore ke database uji memakai potret jumlah baris, memulihkan kedua objek byte-identik, serta menyamarkan email, sesi, token, dan IP audit. Simulasi `pg_dump` gagal tercatat pada `backup_runs` dan memicu alarm ke Superadmin. Container dan jaringan QA telah dihentikan dan dihapus.

**OPS-05 tetap PARTIAL.** Tes tersebut membuktikan jalur backup/restore yang nyata pada QA, tetapi belum membuktikan jadwal harian di lingkungan operasi, tujuan terpisah dari host produksi, serta status sukses yang muncul pada Pengaturan produksi. Konfigurasi tujuan dan kunci penerima masih diperlukan untuk mengaktifkannya.
